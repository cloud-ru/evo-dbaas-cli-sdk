# Полнота CLI относительно Public API

Клиент сгенерирован из OpenAPI и знает весь API. Команды и флаги написаны руками.
Разрыв между ними сам не виден: тесты, ревью и мутационное тестирование проверяют
качество написанного, а не то, чего не написали.

## Зачем отдельная сверка

CLI, сделанный под один сценарий («создать минимальный кластер и подключиться»),
выглядит полным, пока по нему идут этим сценарием. Первый запуск сверки нашёл
25 пропусков: смена пароля и ролей пользователя, изменение топика Kafka, `get`
пользователя, базы и топика; поля `standalone_keeper`, `config`, `logging`,
`parameters`; `--keeper standalone` без `standalone_keeper`; `specs list` по
`cluster_id`; команда в скилле с несуществующим флагом.

Греп имён по коду для сверки не годится: совпадение имени из соседней операции или
поля другого объекта показывает покрытым то, чего нет. Поэтому тест сверяет то,
что реально ушло в сеть, а не имена в коде.

**Вживую не проверены:** выделенный Keeper, `--config`, `--param` кластера,
`--logging`, `users update`, `topics update`, `specs list --cluster-id`, Multi-AZ
(`subnet_ids`), `iam roles revoke`, `iam access-keys delete`, `network vpcs create|delete`.

## Как устроена проверка

`go test ./...` — его запускает любой, кто меняет код, и CI
(`.github/workflows/ci.yml`) на каждый push и pull request.

`TestAPICoverage` (`internal/cmd/coverage_test.go`) гоняет CLI по списку вызовов
против поддельного облака, которое записывает каждый запрос, и сверяет записанное
с `api/openapi-*.yaml`:

1. каждая операция спецификации вызвана;
2. каждое неустаревшее поле тела create/update отправлено (вглубь объектов);
3. каждый параметр запроса отправлен;
4. каждое значение перечисления отправлено хотя бы раз (кроме `*_UNSPECIFIED`);
5. каждый флаг каждой команды встречается в списке вызовов — новый флаг без
   строки в тесте роняет тест, список не может тихо отстать от CLI.

Сеть и IAM — через сгенерированные клиенты `internal/gen/{compute,vpc,iam}`,
но тот же тест: `api/openapi-compute.yaml`, `openapi-vpc.yaml`,
`openapi-iam.yaml` (IAM — Swagger 2.0, тело в параметре `in: body`).
Из этих API сверяются только пути, которые CLI берёт на себя (поле `scope`
в тесте): подсети, VPC, сервисные аккаунты, ключи доступа, роли. Внутри
этих путей — так же полно, с исключениями по причинам.

`TestSkillCommandsParse` — каждая команда из блоков bash в `skills/*/SKILL.md`
существует и её флаги разбираются.

Проверено, что тест кусается: убрать передачу `standalone_keeper` — падает;
исключение без причины — падает; старый скилл Kafka с `--wait` — падает.

## Правила

1. **Источник правды о составе — спецификация, а не сценарий.**
2. **Непокрытое — только исключением с причиной** в `coverageExceptions`
   (`coverage_test.go`) — единственный список. Пустая причина роняет тест.
3. **`--body`** с сырым JSON в create и resize кластеров — новое поле API доступно
   агенту в день выхода, до появления флага.
4. **Свежая спецификация раз в неделю.** Скачать три OpenAPI, сравнить с `api/`.
   Есть разница → перегенерировать клиент → `go test` покажет, что добавить. Так
   приедет, например, Multi-AZ Kafka (сейчас в спецификации одна подсеть).
5. **Живые прогоны по режимам, а не по одному сценарию**: 1×1, выделенный Keeper,
   Multi-AZ, `master-replica` Redis. Платно — при изменении спецификации или кода
   create, не на каждый коммит.
6. **Спецификация не равна правде.** Расхождения, найденные вживую, — в таблицу
   ниже и в проверки живого прогона. Иначе 100 % покрытия по кривой схеме.
7. **Флаг режима передаёт всё, что режиму нужно**, иначе — понятный отказ до
   запроса (как `--keeper standalone`).

## Расхождения спецификации с API

| Где | Спецификация | На деле |
|---|---|---|
| ClickHouse `replicas` | Дополнительные реплики | Хостов на шард; 0 → 400 |
| Redis, Kafka `specs list` | `version_id`, `availability_zone_id` необязательны | Без них 400 (Redis с одной зоной — 500) |
| Redis списки | `page_size` необязателен | Без него 500 |
| ClickHouse `config.*` (10 полей) | `integer` int64, `readOnly` | В ответе строки (`"100"`); в create принимаются и применяются (13.10, `max_connections=100`) |
| ClickHouse `keeper_mode: EMBEDDED` | Ограничений нет | Только 1 шард × 1 реплика × 1 подсеть, иначе 500 |
| ClickHouse без `keeper_mode` (legacy) | Ограничений нет | Только 1×3 или 3×3 и 1 подсеть, иначе 400; multi-AZ — только standalone |
| Compute `POST /api/v1/subnets` | `availability_zone_name` — поле запроса | 422 `extra_forbidden`, нужен `availability_zone_id` (14.10) |
| IAM ответы | camelCase (`serviceAccounts`, `keyId`) | snake_case (`service_accounts`, `key_id`), 14.10 |
| IAM `GET /api/v3/permissions` `filter` | «… AND …» | пробел как «+» — 400 invalid filter; нужен `%20` (14.10) |
| ClickHouse, любой запрос | 403 — нет доступа | 13.10 ~23:00: «failed to verify project access» на 6 из 10 одинаковых запросов; create под этим 403 кластер **создаёт**. Опрос операции повторяется, POST — нет |
